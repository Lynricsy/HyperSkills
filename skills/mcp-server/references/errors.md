## Two error channels, two audiences

MCP separates them deliberately: `[verified]`

| Channel | Shape | For |
|---|---|---|
| Protocol error | JSON-RPC `error` with a code | problems with the request itself: unknown tool, malformed params, server fault |
| Tool execution error | a normal `result` with `isError: true` and content | problems the model can plausibly fix: bad date format, value out of range, missing record, upstream 429 |

Clients should hand tool execution errors to the model so it can self-correct, and *may* hand it
protocol errors, which rarely help. So the classification decides whether the model gets a chance
to recover at all. A recoverable failure returned as a protocol error throws that chance away.

## The SDKs disagree about thrown exceptions

Neither official SDK does what you want when a handler throws. Measured with the same handler body
`raise ValueError("db credentials rejected: user=svc host=10.0.0.5")` /
`throw new Error("db credentials rejected: user=svc host=10.0.0.5")`: `[verified]`

```
# mcp 2.2.0 — the message is discarded; only the traceback reaches stderr
{"result":{"content":[{"text":"Error executing tool boom","type":"text"}],"isError":true,...}}

# @modelcontextprotocol/sdk 1.30.0 and @modelcontextprotocol/server 2.0.0 — verbatim
{"result":{"content":[{"type":"text","text":"db credentials rejected: user=svc host=10.0.0.5"}],"isError":true},...}
```

Both are wrong in opposite directions. Python gives the model `Error executing tool <name>`, which
carries no information it can act on. TypeScript hands the model an internal error string
containing a service account and an internal address, which then sits in the conversation and may
be echoed to the user or to another tool.

So: **do not rely on throwing.** Catch in the handler, decide what the model is allowed to know,
and construct the result yourself. Let exceptions escape only for genuine server faults, and log
the detail to stderr (stdio) or your tracing backend.

```typescript
try {
  return { content: [{ type: "text", text: await fetchNote(id) }] };
} catch (e) {
  process.stderr.write(`notes_get_note ${id}: ${e}\n`);          // full detail, operator-facing
  return {
    isError: true,
    content: [{ type: "text", text: `Note ${id} not found. Use notes_search_notes to find valid ids.` }],
  };
}
```

```python
@mcp.tool()
def notes_get_note(note_id: str) -> str:
    """Return one note's body."""
    try:
        return fetch_note(note_id)
    except NoteMissing:
        raise ToolError(f"Note {note_id} not found. Use notes_search_notes to find valid ids.")
```

Use the SDK's explicit tool-error type where one exists (`ToolError` in `mcp` 2.x) rather than a
bare exception, because that is the path whose message is deliberately forwarded.

## What a good tool execution error says

Three parts, in this order:

1. **What failed, concretely.** `Note n_8f21c3 not found.` Not `Operation failed.`
2. **Why, if the model could not have known.** `Departure date must be in the future; today is
   2026-09-11.`
3. **The next action, naming a tool or parameter.** `Use notes_search_notes to find valid ids.`
   `Retry with limit <= 50.`

Part 3 is what turns a dead end into a recovery. Errors without it produce a retry loop with the
same arguments.

## Writing errors the model can act on

| Situation | Bad | Good |
|---|---|---|
| Unknown id | `404` | `Note n_8f21c3 not found. Use notes_search_notes to find valid ids.` |
| Rate limited | `Error: 429` | `Upstream rate limit hit. Retry after 30s, or narrow the query to fewer notes.` |
| Expired handle | `invalid session` | `Basket bsk_a1b2c3 expired (baskets last 24h idle). Call create_basket to start a new one.` |
| Bad enum | `ValidationError` | `status must be one of open, archived, all — got "closed".` |
| Missing permission | `403` | `The token is missing scope notes.write. This tool needs it; read-only tools still work.` |

Do not put a stack trace in a tool result. It is thousands of tokens of the model's context spent
on frames it cannot act on, and it names internal paths and dependency versions.

## Argument validation errors

Schema validation happens before the handler, so its message is generated by the SDK and goes
straight to the model. In `mcp` 2.2.0 that message is the raw pydantic output, URL and all:
`[verified]`

```
Error executing tool documented: 1 validation error for documentedArguments
city
  Field required [type=missing, input_value={}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.13/v/missing
```

It is usable but leaks the validation library and its version. The practical mitigation is upstream
of the message: a tight, well-described schema means the model gets the constraint from
`inputSchema` and rarely trips the validator at all. See `references/tool-design.md`.

## Protocol errors and code allocation

2026-07-28 partitions the JSON-RPC server-error range: `-32000`…`-32019` stays
implementation-defined with existing SDK usage grandfathered and no new allocations, and
`-32020`…`-32099` is reserved for the specification. `[verified]`

| Code | Meaning |
|---|---|
| `-32602` | invalid params — also the code for a resource that does not exist, and for an invalid pagination cursor |
| `-32601` | method not found |
| `-32603` | internal error |
| `-32020` | `HeaderMismatch` — an HTTP request metadata header disagrees with the body |
| `-32021` | `MissingRequiredClientCapability` |
| `-32022` | `UnsupportedProtocolVersion` — `data.supported` lists what the server does speak |

These three were renumbered in this revision from `-32001` / `-32003` / `-32004`. A server must not
emit the old values, and must not invent new codes inside the reserved range. If you need your own
code, allocate outside both ranges.

Never answer `resources/read` for a missing resource with an empty `contents` array — it is
ambiguous between "exists and is empty" and "does not exist". Return `-32602`. `[official]`

## Do not leak, do not swallow

The two failure modes are symmetric and both are common:

- **Leaking**: forwarding the upstream error verbatim, so connection strings, internal hostnames,
  SQL and tokens end up in the model's context. Log those; send a redacted summary.
- **Swallowing**: catching everything and returning "an error occurred", so the model retries
  identically until the turn ends.

The line to hold: the operator log gets everything, the model gets what it needs to choose
differently next time.

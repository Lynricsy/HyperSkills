## The three layers and who enforces them

| Layer | Lives in | Answers |
|---|---|---|
| Permission | plugin's `permissions/*.toml`, or the app's own | "which commands does this identifier enable, and with which scope?" |
| Capability | `src-tauri/capabilities/*.json`/`.toml` | "which permissions apply to which windows/webviews?" |
| Scope | inside a permission | "which paths, URLs or values may those commands touch?" |

The **runtime authority** in Tauri Core enforces all three. On every invoke it checks that the
calling origin is allowed to use that command, injects any applicable scope into the request,
and only then dispatches. A denied call never reaches the command body, so no amount of
defensive code inside the command can be the fix for a denial.

## What is denied by default and what is not

- **Plugin and `core:` commands are denied** until a capability grants them. This is what
  produces "not allowed"/"permission denied" in the webview console.
- **Your own `#[tauri::command]` functions are allowed** from every window and webview once
  they are registered through `invoke_handler`. Capabilities do not gate them until the build
  script declares a command manifest:

```rust
// src-tauri/build.rs
fn main() {
    tauri_build::try_build(
        tauri_build::Attributes::new()
            .app_manifest(tauri_build::AppManifest::new().commands(&["load_project"])),
    )
    .unwrap();
}
```

With that in place the app's commands become subject to capabilities like any other. Without
it, a failing call to one of your commands is never a permission problem — look at
registration, argument casing or a panic instead.

## Capability files

```json
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main-capability",
  "description": "What the main window may do",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "core:window:allow-set-title",
    "dialog:allow-open",
    { "identifier": "fs:allow-read-text-file",
      "allow": [{ "path": "$APPDATA/projects/**" }] }
  ]
}
```

- Files may be JSON, JSON5 or TOML. **App-defined permissions**, in contrast, may only be TOML.
- **All** files in `src-tauri/capabilities/` are enabled automatically. As soon as
  `app.security.capabilities` is set in `tauri.conf.json`, only the listed identifiers are used
  — a new file then does nothing until it is listed. Set it explicitly when least privilege
  matters; leave it unset only in small apps where "everything in the folder" is the intent.
- Capabilities can be inlined into `app.security.capabilities` as objects, mixed with
  identifiers of files. Inlining is fine for one small capability and unreadable for several.
- Permissions from **every** matching capability merge. Splitting a broad capability into two
  achieves nothing if a third file still targets `["*"]`.

## Targeting windows and platforms

- `windows` matches window **labels**, not titles. `"*"` matches all of them.
- `webviews` targets individual webviews in a multiwebview setup.
- `platforms` narrows a capability to a subset of `linux`, `macOS`, `windows`, `iOS`,
  `android`. Omit it to apply everywhere.

The label is the privilege boundary, so treat labels as a security-relevant naming decision:
a `main` capability and a separate, much smaller `quicknote`/`settings` capability, rather than
one file for the app. Window creation in particular should be reachable only from the
highest-privilege window — otherwise a compromised low-privilege webview spawns a window with
a label that has more permissions.

Per-platform files are also how mobile-only plugins stay out of the desktop build:

```json
{ "identifier": "mobile-capability", "windows": ["main"],
  "platforms": ["iOS", "android"],
  "permissions": ["nfc:allow-scan", "biometric:allow-authenticate"] }
```

## Permission identifiers

- `<plugin>:default` — the plugin's default set. Convenient, and usually wider than needed.
- `<plugin>:allow-<command>` / `<plugin>:deny-<command>` — the autogenerated per-command
  permissions.
- `core:<module>:...` — the built-in modules (`core:app`, `core:event`, `core:window`,
  `core:path`, `core:menu`, `core:tray`, `core:resources`, `core:webview`, `core:image`).
  `core:default` is the bundle of their defaults.
- The `tauri-plugin-` crate prefix is stripped: the crate `tauri-plugin-fs` contributes `fs:…`.
- Identifiers are lowercase ASCII with hyphens and at most one colon. Underscores, uppercase
  and a second colon fail the build with an "identifiers can only include lowercase ASCII…"
  error, which usually points at a plugin name in `Cargo.toml` or a hand-written permission
  file.

Read `src-tauri/gen/schemas/desktop-schema.json` (or `mobile-schema.json`) for the exact set
available to the app after a build, and keep `"$schema"` in each capability file so an editor
completes them.

## Scopes

A scope constrains what an allowed command may touch. `deny` always beats `allow`.

```toml
# a plugin's autogenerated scope permission
[[permission]]
identifier = "scope-applocaldata-recursive"
description = "Recursive access to the whole $APPLOCALDATA folder."
[[permission.scope.allow]]
path = "$APPLOCALDATA/**"
```

```toml
# and the deny that must accompany it on Windows
[[permission]]
identifier = "deny-webview-data-windows"
platforms = ["windows"]
[[permission.scope.deny]]
path = "$APPLOCALDATA/EBWebView/**"
```

The webview's own data lives under `$APPLOCALDATA` (`EBWebView` on Windows), so a recursive
allow there without the matching deny hands the frontend its own cookies and storage. The `fs`
plugin ships `fs:deny-default` for exactly this; keep it in the capability.

Two properties that are easy to misread:

- The scope type is plugin-specific (a glob path for `fs`, a URL pattern for `http`) and is
  passed **to** the command. Enforcement is the command's job, so a scope on a command that
  never checks it is decoration. For app-defined scoped commands, define the scope type and
  enforce it explicitly.
- Path variables (`$HOME`, `$APPDATA`, `$RESOURCE`, …) are resolved at runtime; `**` is
  recursive, `*` is one level.

## App-defined permissions and sets

Permissions for your own commands live in `src-tauri/permissions/*.toml`:

```toml
[[permission]]
identifier = "allow-project-read"
description = "Read project files inside the workspace."
commands.allow = ["load_project", "list_recent"]

[[permission.scope.allow]]
path = "$APPDATA/projects/**"
```

Sets group permissions under one identifier, which is how a capability stays readable:

```toml
[[set]]
identifier = "project-basics"
description = "Everything the project browser needs."
permissions = ["allow-project-read", "fs:read-files", "fs:deny-default"]
```

When authoring a plugin, listing a command in `build.rs`'s `COMMANDS` array generates
`allow-<command>` and `deny-<command>` for it; the plugin's `permissions/default.toml` then
decides which of those users get automatically. Anything genuinely dangerous belongs outside
the default set.

## Remote API access

The IPC is reachable only from bundled code unless a capability opts a remote origin in:

```json
{ "identifier": "remote-capability", "windows": ["main"],
  "remote": { "urls": ["https://*.example.com"] },
  "permissions": ["nfc:allow-scan"] }
```

Use this rarely and with the narrowest permission list in the app. On Linux and Android Tauri
cannot distinguish an iframe from its containing window for this check, so a remote capability
there is effectively granted to anything the page embeds.

## What this model does not protect against

Capabilities reduce the impact of a compromised frontend. They do not make unsafe Rust safe,
do not narrow an over-broad scope, do not enforce a scope the command ignores, and do not help
against a webview zero-day or a compromised build machine. Everything a command receives from
the webview still has to be validated in Rust.

## Diagnosing a denial

1. Read the exact message in the **webview** console; it names the command.
2. Decide whether it is a plugin/`core:` command (capability problem) or one of your own
   (registration problem unless `build.rs` declares a command manifest).
3. Find every capability whose `windows` matches the label of the window that made the call,
   and check the union of their permissions — not just the file you expected to be in use.
4. If `app.security.capabilities` is set, confirm the file you edited is listed there.
5. Look up the precise identifier in `gen/schemas/*-schema.json` rather than pattern-matching
   from another plugin.
6. Add the narrowest permission that covers the call, plus a scope if the command takes a path
   or URL. Re-run and confirm nothing else needed to change.

## Decide whether you need one

Write a provider when a service has a real CRUD API and you need Terraform to own its objects
across plans — drift detection, dependency ordering, destroy. Do not write one to run a script
(that is what `terraform_data` with a `provisioner`, or something outside Terraform, is for),
and do not write one to wrap a CLI whose objects have no stable identity, because there is
nothing for the state to point at.

Check first whether the service already has a provider, or whether a provider-defined function
(Terraform 1.8+/OpenTofu 1.7+) would do — a pure transformation does not need a resource.

## Framework or SDKv2

Use **terraform-plugin-framework** for all new work. Plugin SDKv2 is maintenance-only; new
resources should not be written against it.

A provider can serve both during a migration by muxing with `terraform-plugin-mux`, so
adopting the Framework is never a big-bang rewrite. To tell which mode an existing provider is
in, read `go.mod`:

| `go.mod` contains | Mode |
|---|---|
| `terraform-plugin-mux` | Serves both SDKv2 and Framework resources |
| Only `terraform-plugin-sdk/v2` | SDKv2 |
| Only `terraform-plugin-framework` | Framework |

Migrating existing SDKv2 resources needs care rather than enthusiasm: the Framework
distinguishes null from zero values, so a naive port changes behaviour for users who left an
optional argument unset.

## Repository layout

```
internal/provider/
├── provider.go                 # provider schema + Configure (builds the API client)
├── widget_resource.go
├── widget_resource_test.go     # acceptance tests
├── widget_data_source.go
└── widget_data_source_test.go
docs/
├── resources/widget.md         # generated by tfplugindocs
└── data-sources/widget.md
```

Large multi-service providers split into `internal/service/<service>/` with a file taxonomy
worth copying once a package grows: `consts.go`, `find.go` (finders), `status.go` (status
functions), `wait.go` (waiters), `sweep.go` (test sweepers), `exports_test.go`.

## Resource skeleton

```go
var (
    _ resource.Resource                = &widgetResource{}
    _ resource.ResourceWithConfigure   = &widgetResource{}
    _ resource.ResourceWithImportState = &widgetResource{}
)

type widgetResource struct {
    client *examplecloud.Client
}

func (r *widgetResource) Metadata(_ context.Context, req resource.MetadataRequest, resp *resource.MetadataResponse) {
    resp.TypeName = req.ProviderTypeName + "_widget"
}

// Configure receives whatever the provider's own Configure put in ProviderData.
func (r *widgetResource) Configure(_ context.Context, req resource.ConfigureRequest, resp *resource.ConfigureResponse) {
    if req.ProviderData == nil {
        return // provider not configured yet; this is normal during validation
    }
    client, ok := req.ProviderData.(*examplecloud.Client)
    if !ok {
        resp.Diagnostics.AddError("Unexpected provider data type",
            fmt.Sprintf("Expected *examplecloud.Client, got %T.", req.ProviderData))
        return
    }
    r.client = client
}
```

The interface assertions at the top are how a reader (and the compiler) learns which optional
behaviours the resource implements. The `req.ProviderData == nil` early return is not
defensive coding — `Configure` really is called before the provider is configured, during
validation.

## The four CRUD rules that matter

Everything else about CRUD is mechanical. These four are where providers get it wrong:

1. **Read must handle out-of-band deletion.** When the API says not-found, call
   `resp.State.RemoveResource(ctx)` and return. Returning an error instead means the user can
   never plan their way out of a resource someone deleted in the console.
2. **Delete treats "already gone" as success.** The desired end state is reached; erroring on
   a missing object turns a destroy into a manual state edit.
3. **Update only calls the API for attributes that actually changed.** Compare plan against
   state field by field. A blanket update sends stale values for everything the user did not
   touch.
4. **Create must not return before the object is usable** on an eventually consistent API, or
   the very next resource in the graph fails against an object that does not exist yet.

Import is one line for a single-part identifier:

```go
func (r *widgetResource) ImportState(ctx context.Context, req resource.ImportStateRequest, resp *resource.ImportStateResponse) {
    resource.ImportStatePassthroughID(ctx, path.Root("id"), req, resp)
}
```

For a composite identifier, parse a delimited import ID and set each attribute explicitly.

## Schema design

| Terraform type | Framework attribute | Use for |
|---|---|---|
| `string` | `schema.StringAttribute` | Names, identifiers |
| `number` | `schema.Int64Attribute`, `schema.Float64Attribute` | Counts, sizes |
| `bool` | `schema.BoolAttribute` | Flags |
| `list` | `schema.ListAttribute` | Ordered collections |
| `set` | `schema.SetAttribute` | Unordered unique items |
| `map` | `schema.MapAttribute` | Key/value pairs |
| `object` | `schema.SingleNestedAttribute` | Structured nested configuration |

- The Framework has no magic `id`. Only declare one when the API's identifier really is called
  that; otherwise expose the identifier under its real name and do not invent a duplicate.
- `MarkdownDescription` on every attribute: `tfplugindocs` publishes it, and it is the primary
  user-facing documentation for the resource.
- `stringplanmodifier.RequiresReplace()` on attributes the API cannot change in place —
  omitting it produces an update call that silently does nothing.
- `stringplanmodifier.UseStateForUnknown()` on computed attributes that never change after
  creation, so the plan shows the real value instead of `(known after apply)` and downstream
  resources are not forced to be unknown too.
- Validators on the schema rather than checks in `Create`: a schema validator fails at plan
  time with the attribute path attached.

## Modelling decisions

- A resource is the smallest useful building block. If the API offers CRUD for a thing, it
  probably deserves its own resource.
- One resource talks to one API or service. Cross-service resources break permission scoping,
  auditing and endpoint configuration.
- Data sources are read-only and side-effect free. A singular data source errors on zero or
  multiple matches; a plural one (plural noun in the name) returns a collection and errors on
  neither.
- Attached policies, rule sets, versioned artefacts and long-running task invocations are
  usually their own resources rather than attributes on the parent — that is what lets a user
  manage them independently.
- Start/stop or enable/disable belongs as an attribute *in* the resource, not as a separate
  resource.
- Where the API returns a secret, implement a write-only argument (`*_wo` plus
  `*_wo_version`) so the value never lands in the user's state.

## Eventual consistency

Retry and wait explicitly, in the provider, rather than making users write `time_sleep`:

- A **finder** returns the object or a not-found error.
- A **status function** wraps the finder and returns a status string.
- A **waiter** polls the status function until it reaches a target state, with a timeout the
  user can configure through a `timeouts` block.

Retry on the specific transient errors the API documents, not on every error, and make the
timeout message name the state the resource was stuck in.

## Acceptance tests

Acceptance tests are the provider's real test suite: they run against a live API, gated behind
`TF_ACC=1`, and they cost money and time. They are also the only thing that proves the
resource works.

```go
func TestAccWidget_basic(t *testing.T) {
    rName := acctest.RandStringFromCharSet(10, acctest.CharSetAlphaNum)

    resource.ParallelTest(t, resource.TestCase{
        PreCheck:                 func() { testAccPreCheck(t) },
        ProtoV6ProviderFactories: testAccProtoV6ProviderFactories,
        CheckDestroy:             testAccCheckWidgetDestroy,
        Steps: []resource.TestStep{
            {
                Config: testAccWidgetConfig_basic(rName),
                ConfigStateChecks: []statecheck.StateCheck{
                    statecheck.ExpectKnownValue("example_widget.test",
                        tfjsonpath.New("name"), knownvalue.StringExact(rName)),
                },
            },
            {
                ResourceName:      "example_widget.test",
                ImportState:       true,
                ImportStateVerify: true,
            },
        },
    })
}
```

What the framework gives you for free: each `TestStep` runs plan → apply → refresh → plan, and
fails if that final plan is non-empty. That single behaviour catches most schema bugs —
missing `Computed`, a `Read` that normalises differently from `Create`, an attribute the API
returns in another form — with no assertion written.

- `ConfigStateChecks` with `statecheck`/`knownvalue`/`tfjsonpath` is the current assertion
  style; the older `TestCheckFunc` helpers still work but say less about what failed.
- `resource.ParallelTest` by default; plain `resource.Test` only for tests that cannot run
  concurrently.
- Always include an import step with `ImportStateVerify: true`. It compares imported state
  against applied state attribute by attribute and is the cheapest way to prove `Read` is
  complete.
- Write a "disappears" test (delete the object out of band, expect a non-empty plan) to prove
  rule 1 above.
- Sweepers clean up objects left behind by failed runs; without them a test account accretes
  garbage until quotas fail.

## Documentation

`tfplugindocs` generates `docs/` from the schema descriptions plus `examples/` and optional
`.md.tmpl` templates. That makes the schema's `MarkdownDescription` the single source, and a
stale docs page a missing generation step. Some older large providers still hand-maintain
`website/docs/**.html.markdown`; follow the repository's existing convention when editing one.

## Publishing

- Tag releases as `vX.Y.Z`, with GPG-signed checksums — the registry verifies them.
- Follow semantic versioning against the *schema*: removing an attribute or making an optional
  one required is a major version.
- A provider pinned to an exact version by its consumers is a provider whose users cannot get
  security fixes; document a `~>` constraint as the recommended usage.
